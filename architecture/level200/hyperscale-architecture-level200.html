The write chapter follows one DML statement in autocommit mode, generating change log and a commit record in primary compute's memory log buffer. The Log Service writes incoming blocks to the landing zone and broker cache in parallel. Commit waits for log to harden in the landing zone, not downstream replay. The primary log buffer and Log Service memory/SSD cache are separate. Consumers initiate all log reads, and compute requests the pages it needs (GetPage@LSN). Mint dotted arrows show pulled log and blue arrows show returned pages, each in the direction the data travels; the small ring at the arrow's end marks the component that requested it. Writes and pushes have no ring. In the page-read chapter, Page Servers update cached pages from the returned log in the same step. In the HA chapter, returned log blocks animate from the Log Service into HA in response to those pulls, not as unsolicited pushes; HA does not write log to the service. Shared-page access and log replay are introduced before the read-only app connects. Blue page-return paths run from Page Server to compute. The write chapter separates the landing zone's durability acknowledgment to the engine from the engine's subsequent COMMIT complete response to the app. Page servers replay log for their data slices; compute secondaries replay changes to pages already in their buffer pool or RBPEX. PITR reads snapshots and retained log from storage, not the original database's live Log Service.

Transaction log buffering and write-ahead logging explains that log buffers flush on commit or when full. The animation illustrates logical ordering, not one network request per data modification or physical transport packet boundaries.

The service offloads log to long-term Azure Storage for retention and recovery. This later step is not the initial commit durability point. The zone view illustrates one zone-redundant log service that synchronously replicates log across all zones, Page Servers paired with an active partner in a different zone, and compute distributed (not replicated) across zones. It does not show independent databases or separately configured services in each zone. Log pull and replay timings are illustrative.

Landing-zone durability (original architecture explanation) describes durable log writes; the current architecture reference below documents the memory/SSD log cache and consumers. No historical latency or storage-SKU claims are implied by the animation.

Unlike local HA and named replicas, geo-replicas use another logical server and separate Page Servers and data files. Bootstrap copies data-file snapshots and their recovery log into target storage. Recovery needs sufficient log coverage, not identical snapshot timestamps. Leases protect the log needed for catch-up; the handoff to live replication validates matching log history. The geo-replica's Log Service is a consumer of the primary Log Service: it pulls log blocks across regions, and the geo-secondary compute, its HA replicas, and its Page Servers pull from their local Log Service. Bootstrap is neither a full backup streamed from primary compute nor replay of the entire log history. After recovery and catch-up, the geo-secondary serves reads while asynchronous replication continues. Reads can lag; primary commits do not wait for the geo-secondary.

Active geo-replication

PITR restores file snapshots and replays log to the chosen time within retention. Same-region recovery can restore multi-terabyte databases in minutes, typically without a size-of-data copy; log volume and storage or zone-redundancy changes can increase duration. No fixed restore-time guarantee is implied.
